# T-001: Govern odd_glc Requirements, Graph Design, And Generic Lifecycle Coverage

## STDO Triage

### First Missing Layer

Requirements.

The project already has bootstrap, intent, and product-position surfaces. The
next missing constitutional layer is the first detailed requirement family set.
Graph design must descend from those requirements. Runtime implementation or
tenant activation before that point would recreate the same drift this project
exists to avoid.

### Lawful Re-Entry

`goal_reprice`, then `product_reprice`, then `requirement_reprice`, then
`design_reframe`.

The current `GOALS.md` still describes initial bootstrap capture. This ticket
opens the first requirements/design wave. Once the goal surface names that wave,
the product boundary is repriced to make the generic, any-scale lifecycle scope
explicit before the work descends into requirement authoring and then graph
design.

## Scope

This ticket creates the governing requirements and graph design for `odd_glc`.
It does not build `odd_sdlc`, migrate `odd_sdlc`, or copy `odd_sdlc` behavior.
The first concrete target is the smallest lifecycle that can construct and
prove one Hello World program over GTL/ABG.

The intended downstream result is a clean odd_sdlc start point:

```text
ABG/GTL requirements algebra
  -> odd_glc general lifecycle interpretation
  -> future odd_sdlc specialization
```

## Generic Lifecycle Coverage Target

The product goal is generic lifecycle construction and proof at any scale.
`odd_sdlc` is a witness that the generic model covers a real software-delivery
workflow, and it is a deletion map for local SDLC debt. It is not the driver of
odd_glc structure.

The downstream target is workflow coverage equivalent to `odd_sdlc` without
preserving `odd_sdlc` architecture. Coverage means an operator can recover the
same user-visible lifecycle capabilities through a cleaner dependency chain:

```text
GTL/ABG substrate
  -> odd_glc generic lifecycle framework
  -> downstream odd_sdlc specialization
```

Coverage shall not be measured by whether an `Sdlc*` carrier, local ledger,
phase-flow controller, retry loop, or closure register has been ported. Those
mechanisms are the debt to retire.

## Standing Proof Bar

Every wave that claims proof shall satisfy the proof bar carried from the
T-164/T-165 close:

- execution-grounded: the proof depends on a real actor/operator or admitted
  runtime event, not self-assessment;
- event-sourced and replay-derived: lifecycle truth is read from ABG
  `replayEvents` or public query projections, not side arrays or query-lazy
  invention;
- non-tautological: prompts, declarations, or expected outputs shall not carry
  the answer being proved;
- negative-regression guarded: proof rejects shadow carriers, local emitters,
  local admitted-ref minting, boolean evidence, local fold/residual stores, and
  downstream-public projection emitters;
- F_D/F_P/F_H separated: odd_glc may provide F_P prompt templates and F_H
  decision/policy declarations for ABG to consume. It shall not invoke an F_P
  evaluator, shell a process, or make owner/risk/reprice decisions as runtime
  authority.

## Review Feedback Incorporated

- boundary-authority and ABG-consumption requirement families must precede
  ratified graph design;
- `RequirementSetAsset` authors through GTL requirement declarations or

- downstream programs must use GTL/ABG carriers and ABG runtime truth; odd_glc
  is not a substitute graph catalog, runtime, admission path, fold, residual,
  continuation, or re-entry substrate;
- the proposed `glc.*` catalog is demoted to GTL/ABG system-function bindings
  and, at most, a GTL composition declaration over those system functions;
- `*ViewAsset` surfaces are queries or labels over admitted ABG carriers, not
  native odd_glc carriers;
- the Hello World trace is a scoped forward slice, while general lifecycle
  re-entry remains cyclic.

## Minimal Graph-Design Target

The graph design must name the first minimal Hello World-capable lifecycle
trace:

```text
observe gap
-> frame problem
-> select solution space
-> derive product/requirement pressure
-> project requirement environment
-> select destination topology
-> construct instruction set
-> bind evidence view
-> fold assurance view
-> project residual pressure
-> route re-entry, release, block, or downstream specialization
```

This is a lifecycle binding target over GTL/ABG system-function carriers, not an
imperative controller loop or odd_glc-owned graph catalog.

### GTL Composition Shape

The lawful graph-design target is a GTL composition declaration over the bound
system functions, not a new odd_glc graph-function catalog:

```text
abg.requirements.route_context_constraint
-> abg.requirements.compile_edge_environment
-> abg.requirements.project_edge_obligations
-> ABG actor/operator invocation and payload admission
-> abg.requirements.bind_evidence
-> abg.requirements.fold_requirement_state
-> abg.requirements.project_assurance_case
-> residual and attenuation projection
-> ABG continuation/re-entry disposition
```

`odd_glc` may name lifecycle stages over that composition and attach policy,
F_P/F_H, query, proof-interpretation, and specialization constraints. It shall
not publish those generic functions as native `glc.*` functions.

### F_D, F_P, And F_H Boundaries

| Boundary | Owns | Candidate checks or judgments |
| --- | --- | --- |
| `F_D` | Finite structural checks over admitted states. | Required asset presence, URI/ref shape, declared asset type, span coverage, evidence-ref presence, digest presence, command result shape, no missing capability asset. |
| `F_P` | Semantic lifecycle judgment over the current trace. | Whether the product definition matches the intent, whether the requirements express the requested outcome, whether observed output satisfies the declared greeting, whether residual pressure is semantically cleared. |
| `F_H` | Owner decision under uncertainty or policy. | Reprice target, accept minimal proof, block on missing capability, choose downstream specialization, decide whether Hello World closure is enough for first realization work. |

### GTL/ABG Dependency Points

| Dependency | Consumed truth | odd_glc interpretation |
| --- | --- | --- |
| GTL/ABG graph-function catalog carrier | System graph-function publication surface. | Lifecycle slots bind GTL/ABG-published graph functions; odd_glc does not publish a catalog. |
| GTL graph vector | Typed `A -> B` traversal identity. | Vectors bind asset transitions and requirement spans. |
| GTL node/interface/asset surface | Typed carrier declarations. | Asset types and bindings stay inspectable and typed. |
| ABG requirement ledger projection | Active requirements, spans, contexts, folds, residuals. | `RequirementEnvironmentViewAsset` is read-only lifecycle interpretation. |
| ABG actor/operator invocation | Side-effecting process execution and admitted run result. | `CapabilityAsset` declares need; `odd_glc` does not shell out or supervise. |
| ABG payload/evidence admission | Admitted evidence refs and provenance. | `EvidenceBindingAsset` binds evidence to requirements without owning admission. |
| ABG assurance fold | Closure projection. | `AssuranceFoldViewAsset` interprets closure state without defining closure truth. |
| ABG continuation/re-entry | Runtime disposition truth. | `ReentryDecisionAsset` maps disposition into lifecycle meaning. |

### Downstream Program Rule

Downstream programs that specialize odd_glc must use GTL/ABG:

- graph structure, graph vectors, graph functions, modules, jobs, interfaces,
  and asset surfaces are GTL/ABG carriers;
- execution, payload admission, evidence admission, assurance fold, residual,
  continuation, replay, and re-entry are ABG runtime truth;
- odd_glc supplies lifecycle meaning, read/query interpretation, policy
  overlays, proof interpretation, and specialization constraints;
- odd_glc does not provide a replacement graph catalog, runtime, admission
  path, evidence store, fold, residual, continuation, or re-entry substrate.

### Upstream Readiness Gate

Each consuming lifecycle binding must classify its required GTL/ABG capability
before ratification:

| Readiness state | Ratification effect |
| --- | --- |
| `ready` | Binding may ratify if local requirements and proof expectations are met. |
| `missing` | Binding defers or blocks. |
| `placeholder` | Binding defers; carrier presence is not closure. |
| `test_only` | Binding defers; fixture coverage is not runtime capability. |
| `unwired` | Binding defers until runtime, replay, admission, fold, residual, continuation, or query path is connected. |
| `unpinned` | Binding defers until consumed substrate identity is pinned. |

Requirement-environment, assurance-fold, residual-pressure, and re-entry
interpretation are the first lifecycle slots that must fail closed when ABG
cannot answer the required lifecycle questions from admitted carriers and
replay truth.

### Re-Entry Shape

Slice 1 proves the forward Hello World thread and one terminal disposition:
release/readiness, repair, reprice, or block.

The general lifecycle graph is cyclic. Residual pressure can route through
ABG-owned re-entry facts back to an earlier lifecycle span. Ratified design
must preserve that cycle instead of treating re-entry as a terminal-only phase.

### Review Questions

- Is the Hello World graph still minimal, or does any function imply full SDLC
  scope before odd_sdlc specialization?
- Does every composition slot name the GTL/ABG system function or carrier it
  consumes and fail closed when that capability is not `ready`?
- Does every downstream program path still use GTL/ABG as the graph and
  runtime substrate?
- Are any assets missing for executable proof, especially capability,
  evidence-binding, fold, residual, or re-entry assets?
- Does any function duplicate ABG traversal, admission, fold, continuation, or
  replay truth?
- Does any lifecycle slot hide construction inside an imperative service,
  odd_glc-native graph function, or operator checklist instead of binding a
  GTL/ABG system function?
- Are the F_D/F_P/F_H boundaries sufficient to prove a Hello World trace while
  preserving semantic judgment and owner decisions outside deterministic
  checks?
- Is `TargetArtifactAsset` generic enough that the Hello World program remains
  specialization data rather than odd_glc software policy?
- Is the slice-1 forward thread clearly scoped away from the general cyclic
  re-entry model?

## odd_sdlc Clean-Start Boundary

The clean start for odd_sdlc is a specialization contract, not a migration
shortcut.

The contract must say:

- which odd_glc lifecycle bindings over GTL/ABG graph functions odd_sdlc may
  specialize;
- which software-domain terms remain outside odd_glc generic law;
- which ABG requirements-algebra projections odd_sdlc consumes;
- which proof/query surfaces odd_sdlc may extend;
- which local odd_sdlc ledgers/controllers are not allowed to reappear.
